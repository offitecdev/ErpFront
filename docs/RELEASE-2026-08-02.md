# Release 02.08.2026 — what changed and where

This document explains, item by item, every change that went into the
**02.08.2026** release of the Offitec management panel (`offitec-frontend`),
with the exact files and line ranges to look at.

It is written for someone who has **never seen this codebase before**. Each
item follows the same shape:

> **What the customer asked for** → **what it looks like in the app** →
> **which code does it** → **why it was built that way**.

## Where the requests came from

Two documents drive this release. Both are shipped with the app so anyone can
read the original:

| Document | Shipped as | Used for |
| --- | --- | --- |
| `Korrekturen020826.pdf` — *„Erbetene Korrekturen und Ergänzungen für die Angebotsmaske"* | `public/updates/OMP-Update-2026-08-02.pdf` | Items 1–3 below. Downloaded from the update popup on the login page. |
| `OMP-Auftrag - Lieferant.pdf` — *„Wie wird eine Auftragserteilung an den Lieferanten erstellt?"* | `public/guides/OMP-Auftrag-Lieferant.pdf` | Item 8 below. The source text of the German order instructions. |

## Orientation — 60 seconds on the project

* React + TypeScript + Vite. Source lives in `src/`, page components in
  `src/pages/`, shared building blocks in `src/components/`.
* **Three languages** (DE / EN / TR). Strings come from
  `src/i18n/locales/*.json` through `t('namespace.key')`. Never hardcode UI
  text — the one documented exception is the login-page order guide (item 8),
  and the reason is written into that file.
* Styling is Tailwind utility classes plus a handful of hand-written
  stylesheets in `src/styles/` for the bigger surfaces (e.g. `login.css`).
  Dark mode is driven by a `dark` class on `<html>`.
* The app is **moving off Ant Design** (item 6). New surfaces are written as
  plain TypeScript components; antd only survives where it has not been
  replaced yet.

# Part A — The corrections requested in „Korrekturen 02.08.2026"

## 1. Address type corrected

**Request (PDF page 1, item 1).** In the customer profile, the main address
block should read as separate labelled entries — *Adressname, Adresse, PLZ,
Stadt, Zuständiger Mitarbeiter* — instead of one merged "Address" field.

**In the app.** CRM → open a customer → the *Hauptadresse* card now shows three
distinct rows: **Adresse**, **PLZ**, **Stadt**. Clicking any one of them puts
all three into edit mode at once, and they are saved as a single block. The
addresses table underneath shows the same three values in their own columns.

**Code.**

| File | What to look at |
| --- | --- |
| `src/pages/crm/detail/CustomerInfoCard.tsx` | The `addressField()` helper (~line 161). It renders one row per key but all three share the `'address'` open-state key — that is what makes one click open the whole block. |
| `src/pages/crm/detail/CustomerAddressesTable.tsx` | ~line 194. The primary-address row used to render a merged `<AddressLines>` across `colSpan={3}`; it now emits `address`, `postalCode` and `city` as three real `<td>`s so it lines up with the editable rows below it. |
| `src/components/ui-shared/AddressFields.tsx` | Gained two props: `fields` (render only the listed sub-fields) and `labels` (override individual labels). See the doc comment at the top. |
| `src/components/ui-shared/addressForm.ts` | `AddressFormValue`, `toAddressForm()`, `toAddressPayload()` — the shared shape and the conversion to/from the API payload. |
| `src/utils/address.ts` | `formatAddressLines()` — the display rule used everywhere else. |

**Why it was built this way.** Two rules are worth knowing before touching
address code:

1. **There is no single field called "Address."** A postal address is always
   composed of distinct parts (street, supplement, postal code, city, state,
   country). This is why `AddressFields` exists at all.
2. **Hiding a sub-field never deletes it.** `fields` only controls what is
   *drawn*. Hidden parts are still loaded into the form and still sent back on
   save, so narrowing a form cannot silently wipe data on an existing record.
   The supplier form uses this to show just *Adresse / PLZ / Stadt*; CRM and
   offer forms keep the full component labels.

**Request (PDF page 1, item 2).** The offer's introductory letter

**In the app.** Offer detail → *PDF-Inhalt*. The block is headed *„Diese Blöcke
sind optional und erscheinen nur ausgefüllt im PDF."* The intro text has a
formatting toolbar (bold, italic, underline, strikethrough, colour, bullet

**Code.**

| File | What to look at |
| --- | --- |
| `src/pages/tender/detail/components/pdf/TenderPdfContentPanel.tsx` | The whole panel (522 lines). `coverLetter` is the intro text; `showCoverLetter` (line 134) decides whether the block is drawn at all — an empty block never reaches the PDF. |

**Why it was built this way.** The optional PDF blocks are deliberately
*absent* rather than empty when unused: an offer without an intro letter must
not print a blank region where the letter would have been.

## 3. Reusable template text, corrected address format, reference-seller commission

**Request (PDF page 2, item 3).** Three things at once: a selected draft must
be usable as a template, the address format on the offer had to be corrected,
and the *commission for the reference seller* had to be added — with more
entries to follow over time.

### 3a. Draft → reusable template (Textbaustein)

Templates are stored per tenant, so everyone in the company shares them.

| File | What to look at |
| --- | --- |
| `src/types/tender.ts` (~line 158) | `TenderTextTemplateDto` — `id`, `tenantId`, `title`, `content` (rich HTML), `isDefault`. `isDefault` marks the template pre-filled into new offers; the screenshot in the request PDF shows it as the `STANDARD` chip. |
| `src/lib/api/tender.ts` lines 477–495 | `listTextTemplates` / `createTextTemplate` / `updateTextTemplate` / `deleteTextTemplate`. |
| `TenderPdfContentPanel.tsx` line 198 | `applyTemplate()` — clicking a template copies its content into `coverLetter` and opens the block. |
| `TenderPdfContentPanel.tsx` line 171 | `saveTemplateForm()` — *„Aktuellen Text als Vorlage speichern"* creates a new template from whatever is in the editor. |

The template list is fetched **once** and then cached in component state
(`loadTemplates()` returns early if `templates` is already set), so reopening
the picker does not hit the network again.

### 3b. Address format on the offer

The offer's recipient block prints whole address lines and shrinks the text to
fit rather than wrapping — a recipient block that wraps mid-address looks
broken in a window envelope. See `src/utils/pdf/tenderPdfModern.ts`; the
on-screen counterparts are the *Lieferadresse / Projektadresse* and
*Rechnungsadresse* rows in `src/pages/tender/TenderDetail.tsx` (~line 1155).

### 3c. Commission for the reference seller

The offer's cover info card now carries three related entries — matching the
request PDF exactly:

| Row | Field | Where the value comes from |
| --- | --- | --- |
| **Kommission** | `Tender.commissionNumber` | Typed by the user |
| **Referenz** | `Tender.customerReference` | Typed by the user (the customer's own reference) |
| **Verkäufer** | `createdByName` | Derived — the employee who created the offer |

| File | What to look at |
| --- | --- |
| `src/pages/tender/detail/components/info/TenderCommissionInput.tsx` | The inline input. It commits on **blur or Enter**, not per keystroke — otherwise every character would stage a separate meta change. It is reused verbatim for the *Referenz* row, which is why it takes an `ariaLabel` override. |
| `src/pages/tender/TenderDetail.tsx` lines 1136–1151 | The two rows in the `customer` group, each wired to `handleMetaFieldChange`. |
| `src/types/tender.ts` lines 30, 32 | `commissionNumber`, `customerReference`. |
| `src/lib/api/tender.ts` lines 161–163 | The same two fields in the update payload. |
| `src/utils/pdf/tenderPdfModern.ts` lines 805–815 | The cover info card. **Referenz sits directly above Verkäufer** — both answer "who / where from", so they belong together. Labels per language are at lines 158–162 (TR), 192–196 (DE), 226–230 (EN). |

**Why it was built this way.** The request says *„weitere Einträge werden im
Laufe der Zeit hinzugefügt"* (more entries will follow). The info card is
therefore built from a **data array** (`tenderDetailGroups` in
`TenderDetail.tsx`), not from hand-placed markup — adding the next entry means
appending one object, not rebuilding the layout.

# Part B — The larger reworks in this release

## 4. Project plans and reports revised

**What changed.** Report lists no longer carry the report *content*. The
checklist answers (the table in the PDF) and the customer signature are
fetched only when a PDF is actually produced, for that one report.

**Code.**

| File | What to look at |
| --- | --- |
| `src/lib/api/project.ts` (~line 53) | `ServiceReportDto`: `operationsDone`, `technicalNotes` and `customerSignature` became **optional** and carry a comment saying they are not in the list response. |
| `src/lib/api/project.ts` line 548 | `deliveryReportApi.getOne(id)` — the full record. |
| `src/pages/crm/CustomerReports.tsx` (~line 286) | The list row and the detail record are merged (`{ ...row, ...full }`) and the project is fetched **in parallel** via `Promise.all`. |
| `src/pages/services/ServiceReports.tsx` (~line 124) | The same pattern in the services module. |

**Why the merge order matters.** The list row carries *enriched labels* the
detail record does not have, so the row forms the base — but the detail record
is spread **on top**, because it is the only one of the two that holds the
report content. Keep it as `{ ...row, ...full }`.

Also new in this release: `projectApi.listPicker()` (`src/lib/api/project.ts`
~line 111) — a lean project + order list for pickers, with a 15-second timeout
so a hanging request cannot leave the calendar wizard stuck on "loading".

* Appointments and meeting activities both carry `ccEmails`, which is why
  `projectApi.createAppointment` gained a `ccEmails` parameter
  (`src/lib/api/project.ts` ~line 323).

## 6. Ant Design → own TypeScript components

**What changed.** New and rebuilt surfaces no longer use antd. antd remains
only in the ~24 files that have not been converted yet; nothing new is being
added to that list.

**The replacements.**

| File | Replaces |
| --- | --- |
| `src/components/ui-shared/ConfirmDialog.tsx` | `window.confirm()` **and** antd's `Modal.confirm`. Hand-written portal, ESC and backdrop cancel, the confirm button takes focus on open, and `busy` locks both buttons so an async action cannot be double-fired. |
| `src/components/ui-shared/TableKit.tsx` | antd `Table` on converted pages |
| `src/components/ui-shared/BottomSheet.tsx` | antd `Drawer` |
| `src/components/ui-shared/Loader.tsx` | antd `Spin` |
| `src/components/icons/lucideLocal.tsx` | `@ant-design/icons` — 101 locally inlined icons, so icon usage costs no external package |
| `src/components/icons/antIconCompat.tsx` | A shim keeping the old antd icon names working while files are converted one at a time |
| `src/components/login/LoginPopup.tsx` | antd `Modal` on the login page (new in this release — see item 7) |

**Why not just swap the imports?** antd modals bring their own portal, focus
trap and z-index stack. Mixed with the hand-written popup layers in inventory
and calendar, two competing stacking systems fight over which dialog is on
top, and antd overrides the app's dark-mode colours. The rule that came out of
that: **a module either uses antd popups or hand-written ones, never both.**
`ui-shared/Modal.tsx` is still antd-based and is deliberately *not* used inside
the converted modules.

# Part C — Login page: update notice and order instructions

This is the part implemented in this task. All three changes are on the
**login page** (`/login`).

## 7. Update notification popup (02.08.2026)

**Request.** Announce the 02.08.2026 update as a popup with a **Download PDF**
option, and make sure it never comes back once closed.

**In the app.** The first time anyone opens `/login` after this release, a card
drops in above the sign-in form: kicker **UPDATE**, headline **„Neue Version
vom 02.08.2026"**, a six-point summary of this release, and two buttons —
**„PDF herunterladen"** and **„Schliessen"**. Close it once and it is gone for
good.

**Code — `src/components/login/LoginUpdateNotice.tsx`.**

| Constant / function | Purpose |
| --- | --- |
| `UPDATE_RELEASE_DATE` | `'02.08.2026'` — shown in the headline |
| `DISMISS_KEY` | `'offitec-update-notice-2026-08-02'` — the localStorage flag |
| `UPDATE_PDF_URL` | `` `${import.meta.env.BASE_URL}updates/OMP-Update-2026-08-02.pdf` `` |
| `HIGHLIGHTS` | The six summary lines (items 1–6 of this document, in one sentence each) |
| `readDismissed()` | Reads the flag; returns `false` if storage throws |
| `dismiss()` | Closes **and** writes the flag |

Three design decisions worth understanding:

1. **The dismiss key carries the release date.** A future update gets a new key
   and therefore shows again, exactly once — without anyone having to clear old
   entries. This is the same versioning trick the previous popup used.
2. **`localStorage` access is wrapped in `try`/`catch` in both directions.** In
   private mode or with cookies blocked, even *reading* throws. On a read
   failure the notice shows (safe default); on a write failure closing still
   works immediately, it just is not remembered.
3. **`BASE_URL`, not a leading `/`.** The Electron build ships with a relative
   base (`vite.config.ts` line 10) — an absolute `/updates/...` would resolve to
   nothing there.

The download is a plain `<a download="…">`; the `download` attribute makes the
browser save the file instead of opening it in the built-in viewer. Downloading
deliberately **does not** close the notice — only the ✕, the *Schliessen*
button and <kbd>Esc</kbd> do that, and all three go through `dismiss()`.

## 8. „Produktionsprototyp Türkei" link → German order instructions

**Request.** Remove the Turkey prototype link, and put instructions on how to
place an order in its place. Write the text directly in German — no
translation. Give it its own component.

**In the app.** The quick-access card at the bottom left now reads
**Anleitung / „Wie erteile ich einen Auftrag?"**. Clicking it opens a wide,
scrollable guide titled *„Wie wird eine Auftragserteilung an den Lieferanten
erstellt?"* with all **15 steps**, grouped into four sections, plus an
**„Anleitung als PDF"** download.

**Code.**

| File | Role |
| --- | --- |
| `src/components/login/LoginOrderGuide.tsx` | The component. Contains **both** the dock card (the trigger) and the guide popup, so the login page only has to render `<LoginOrderGuide />`. |
| `src/components/login/orderGuideContent.ts` | The text, as typed data (`OrderGuideSection[]` / `OrderGuideStep[]`). |
| `public/guides/OMP-Auftrag-Lieferant.pdf` | The original training document, offered for download. |

**The four sections and 15 steps** (condensed from the source PDF):

| Section | Steps | Covers |
| --- | --- | --- |
| *Auftrag erfassen* | 1–6 | New order, order vs. price request, adding positions / Excel import, the three calculation modes, per-line decisions, extra fees |
| *Details, Lieferant und Versand* | 7–10 | Order details and reusable preface text, assigning the supplier, save-as-draft vs. confirm, mailing the PDF |
| *Wareneingang und Bestand* | 11–12 | Booking goods receipt, viewing stock movements |
| *Von der Preisanfrage zum Kaufauftrag* | 13–15 | Creating a price request, mailing it, converting it into a purchase order |

Two step types get special treatment in the markup: `bullets` (used for the
three calculation modes — *Direkte Eingabe*, *Automatische Berechnung*,
*Berechnung auf Basis der Liefermenge*) and `hint`, a highlighted box carrying
the warnings from the training document (the Excel header rule; losing direct
purchase calculations if you calculate automatically in bulk and then save).

**Why the text is not translated.** This is the one place in the app where
hardcoded German is correct, and the reason is written at the top of
`orderGuideContent.ts`:

* The guide is read **before login**, so there is no user and therefore no
  language preference yet.
* It quotes the German button labels literally (*„Neuer Auftrag"*,
  *„Bestellung bestätigen"*, *„Bestandsbewegungen"*). Translating the prose
  would decouple the instructions from the buttons they describe.

Everything else on the login page keeps using `t(...)` as normal.

**Why the content is data, not JSX.** `orderGuideContent.ts` holds the steps as
plain objects. Editing the guide means editing that file; the component only
renders. Anyone maintaining the text never has to read JSX.

## 9. The old prototype popup, removed

The previous popup — which pointed at `https://prototip.offitec.ch/` — is gone
in full. Nothing of it remains: verified at runtime that no element with a
`proto` class exists on the page.

**What was deleted.**

| Location | Removed |
| --- | --- |
| `src/pages/Login.tsx` | `PRODUCTION_PROTOTYPE_URL`, `PROTOTYPE_RELEASE_DATE`, `LOGIN_GUIDE_DISMISSED_KEY`, the `showGuidePopup` state, `dismissGuidePopup()`, the `<a>` in the resource dock, and the ~45-line `AnimatePresence` popup block |
| `src/styles/login.css` | The entire `ofi-login2__proto-*` rule set — light mode, dark mode and the mobile media query |

`Login.tsx` now holds **no popup state and no storage key at all**: both new
components own their own state. The page just renders them.

## The shared popup frame

Both new popups sit on one frame — `src/components/login/LoginPopup.tsx`.

| Prop | Effect |
| --- | --- |
| `size` | `'md'` (580 px, the notice) or `'lg'` (900 px, the guide) |
| `backdrop` | `false` (default): the layer sets `pointer-events: none`, so **the sign-in form behind stays fully usable** and only the card catches clicks. `true`: dimmed backdrop, clicking beside the card closes it. |
| `titleId` | Wired to `aria-labelledby`, so screen readers announce the card by its heading |
| `kicker` / `icon` / `footer` | Header label, header icon, action bar |

<kbd>Esc</kbd> closes in both modes. The listener is on `document`, not on the
card, because the card does not necessarily hold focus — with `backdrop: false`
the focus stays in the sign-in form, which is the whole point of that mode.

Layout is header / body / footer in a flex column: **only the body scrolls**,
so the title and the download button stay visible in the 15-step guide no
matter how far down you are.

**Styles** live in `src/styles/login.css` under
`/* ---- Popups der Anmeldeseite ---- */` — the `ofi-login2__dlg-*` and
`ofi-login2__guide-*` blocks that replaced the deleted `proto` rules. Dark mode
gets the app's gold accent (`#e6cf9e`); note the `!important` on
`.dark .ofi-login2__dlg-btn` — `dark.css` paints every plain `<a>` gold in dark
mode, which would otherwise render the download button gold-on-gold.

One more detail: `.ofi-login2__resource-card` is now used by a `<button>`
instead of an `<a>` (the card opens a popup, it does not navigate). The rule
gained `font: inherit`, `text-align: left`, `width: 100%` and `cursor: pointer`
so the button does not inherit browser defaults and look different from before.
